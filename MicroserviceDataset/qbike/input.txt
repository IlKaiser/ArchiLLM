# SYSTEM DESCRIPTION:
QBike is a microservices-based ride-sharing platform specifically designed for electric bikes in congested urban environments, serving as an alternative to traditional ride-hailing services during peak traffic hours. The system enables electric bike drivers to publish their location and availability while allowing passengers to submit real-time trip requests with pickup and destination points, which are then automatically matched by the platform's intelligent matching algorithm. Built using Spring Cloud microservices architecture with domain-driven design principles, the platform includes user management, intention matching, order processing, position tracking, and API gateway services, all orchestrated through Docker containers and supported by Redis, MySQL, RabbitMQ, and distributed tracing capabilities. The system targets urban commuters seeking flexible transportation solutions during rush hours when traditional vehicles face traffic congestion.

# USER STORIES:
1. As a driver, I want to register my account so that I can start offering electric bike rides.
2. As a driver, I want to update my current location so that passengers can find me nearby.
3. As a driver, I want to set my availability status so that the system knows when I'm ready to accept rides.
4. As a driver, I want to receive ride requests from nearby passengers so that I can earn income.
5. As a driver, I want to accept or decline ride requests so that I can choose which trips to take.
6. As a driver, I want to view passenger pickup and destination locations so that I can plan my route.
7. As a driver, I want to update my status when I pick up a passenger so that the system tracks the trip progress.
8. As a driver, I want to mark a trip as completed so that I can receive payment and become available for new rides.
9. As a passenger, I want to register my account so that I can request electric bike rides.
10. As a passenger, I want to submit a trip request with pickup and destination locations so that I can get transportation.
11. As a passenger, I want the system to automatically match me with nearby available drivers so that I don't have to search manually.
12. As a passenger, I want to see which driver has been assigned to me so that I can identify them at pickup.
13. As a passenger, I want to track my driver's location in real-time so that I know when they will arrive.
14. As a passenger, I want to confirm my intention to take a ride so that the booking process can proceed.
15. As a passenger, I want to modify my trip destination during the ride so that I can adapt to changing plans.
16. As a passenger, I want to rate my driver after the trip so that I can provide feedback on the service quality.
17. As a system administrator, I want to monitor all active drivers' locations so that I can optimize the matching algorithm.
18. As a system administrator, I want to view ride matching statistics so that I can analyze platform performance.
19. As a system administrator, I want to track order states and transitions so that I can ensure proper workflow execution.
20. As a system administrator, I want to monitor system health through distributed tracing so that I can identify and resolve issues.
21. As a system, I want to calculate optimal driver-passenger matches based on proximity so that wait times are minimized.
22. As a system, I want to handle driver unavailability gracefully so that passengers can be matched with alternative drivers.
23. As a system, I want to maintain driver position data in real-time so that matching accuracy is maximized.
24. As a system, I want to process trip intentions asynchronously so that the platform remains responsive under load.
25. As a system, I want to implement distributed locking for driver assignments so that multiple passengers cannot book the same driver simultaneously.
26. As a system, I want to manage order state transitions using finite state machines so that trip workflows are consistent and reliable.
27. As a system, I want to persist trip and user data reliably so that information is not lost during system failures.
28. As a system, I want to route API requests through a gateway so that microservices can be managed centrally.
29. As a system, I want to implement circuit breakers for service calls so that cascading failures are prevented.
30. As a system, I want to provide service discovery capabilities so that microservices can locate each other dynamically.
